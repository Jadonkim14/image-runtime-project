# V0.2 — Baseline Benchmark

## V0.2-A — Process-per-Image Baseline Benchmark

### 1. 목표

V0.1에서 정상 실행을 확인한 OpenVINO 이미지 분류 프로그램을 수정하지 않은 상태에서 반복 실행하여 초기 성능 baseline을 확보한다.

이 단계에서는 다음을 하지 않는다.

* Thread 추가
* Async inference 적용
* Pipeline 구성
* Scheduler 구현
* Memory optimization
* GPU scheduling

현재 목적은 최적화가 아니라 **기존 실행 구조의 성능을 측정하고 기록하는 것**이다.

### 3. V0.2-A Benchmark 방식

현재 OpenVINO sample은 기본적으로 이미지 한 장을 처리하고 종료한다.

따라서 V0.2-A에서는 프로그램 코드를 수정하지 않고 shell loop를 사용하여 동일한 프로그램을 100회 반복 실행했다.

```bash
/usr/bin/time -v bash -c '
for i in $(seq 1 100); do
    /home/jadonkim14/openvino_c_samples_build/intel64/Release/hello_classification_c \
        models/squeezenet1.1-7.onnx \
        data/images/banana.bmp \
        CPU > /dev/null
done
'
```

프로그램의 Top-10 결과 출력은 benchmark에 영향을 줄 수 있으므로 다음과 같이 stdout을 `/dev/null`로 보냈다.

```bash
> /dev/null
```

이 benchmark는 이미지 100장을 하나의 프로세스에서 연속 처리하는 것이 아니다.

실제 구조는 다음과 같다.

```text
Program Start
↓
Model Load / Compile
↓
Image Processing
↓
Inference
↓
Program Exit
```

위 과정 자체를 100번 반복한다.

따라서 본 결과는 순수 inference throughput이 아니라 **process-per-image 실행 방식의 baseline**이다.

3회의 평균 전체 실행시간은 다음과 같다.

```text
(20.34 + 20.46 + 21.36) / 3
```


```text
100 / 20.72
≈ 4.83 executions/s
```

```text
Average Throughput ≈ 4.83 executions/s
```

이다.

여기서 `images/s` 대신 `executions/s`라고 기록하는 이유는 각 이미지마다 새로운 프로세스가 생성되고 모델 로딩 및 컴파일까지 다시 수행되기 때문이다.

### 6. CPU 사용량

측정된 CPU utilization은 다음과 같다.

```text
204%
205%
208%
```

Linux에서 CPU 사용률 100%는 일반적으로 CPU core 하나를 완전히 사용하는 수준으로 이해할 수 있다.

따라서 현재 benchmark에서는 평균적으로 약 2개 정도의 CPU core에 해당하는 CPU 시간이 사용되고 있다.

예를 들어 Run 1에서는:

```text
User time   = 16.13 s
System time = 25.49 s

Total CPU time = 41.62 s
```

실제 경과시간은:

```text
20.34 s
```

이므로:

```text
41.62 / 20.34
≈ 2.046
```

이고, 이는 측정된:

```text
204%
```

와 거의 일치한다.

### 7. Memory 사용량

Maximum Resident Set Size는 다음과 같다.

```text
Run 1: 74412 KB
Run 2: 74492 KB
Run 3: 74544 KB
```

이를 MiB 단위로 환산하면 약:

```text
72.7 ~ 72.8 MiB
```

이다.

Maximum RSS는 프로그램 실행 중 실제 RAM에 올라와 있던 메모리의 최대치를 의미한다.

100번의 실행에서 사용된 메모리를 합친 값이 아니라, benchmark 실행 중 관측된 최대 resident memory 크기이다.

3회 모두 거의 동일한 값이 측정되었기 때문에 현재 workload에서 peak memory usage는 비교적 안정적이다.

### 8. Page Cache 관련 관측

Run 1과 Run 2에서는 다음과 같이 major page fault와 filesystem input이 발생했다.

```text
Run 1
Major page faults: 723
File system inputs: 125912

Run 2
Major page faults: 721
File system inputs: 126072
```

반면 Run 3에서는:

```text
Major page faults: 0
File system inputs: 0
```

이 측정되었다.

이는 OS page cache의 영향을 받았을 가능성이 있다.

앞선 실행에서 모델 및 이미지 관련 데이터가 page cache에 들어가면서 이후 실행에서는 실제 storage 접근 없이 메모리에서 데이터를 가져왔을 가능성이 있다.

다만 V0.2-A의 목적은 병목 분석이 아니므로 현재 단계에서는 해당 현상을 최적화 대상으로 판단하지 않는다.

추후 benchmark 설계에서는 다음 두 조건을 구분할 필요가 있다.

```text
Cold Cache
vs
Warm Cache
```

### 9. Per-Run Latency 측정

전체 100회 benchmark의 총 실행시간뿐 아니라 각 프로그램 실행의 latency 분포를 확인하기 위해 각 실행시간을 별도로 저장했다.

사용 명령:

```bash
rm -f latency.txt

for i in $(seq 1 100); do
    /usr/bin/time -f "%e" \
        /home/jadonkim14/openvino_c_samples_build/intel64/Release/hello_classification_c \
        models/squeezenet1.1-7.onnx \
        data/images/banana.bmp \
        CPU \
        > /dev/null 2>> latency.txt
done
```

저장된 sample 개수 확인:

```bash
wc -l latency.txt
```

결과:

```text
100 latency.txt
```

총 100개의 per-run latency sample이 정상적으로 저장되었다.

### 11. P95 / P99 Latency

먼저 latency 값을 오름차순으로 정렬했다.

```bash
sort -n latency.txt > latency_sorted.txt
```

100개의 sample에서 95번째와 99번째 값을 확인했다.

```bash
echo -n "P95: "
sed -n '95p' latency_sorted.txt

echo -n "P99: "
sed -n '99p' latency_sorted.txt
```

결과:

```text
P95: 0.23
P99: 0.27
```

밀리초로 변환하면:

```text
P95 Latency = 230 ms
P99 Latency = 270 ms
```

이다.

의미:

```text
P95 = 전체 실행의 약 95%가 230 ms 이내에 완료
P99 = 전체 실행의 약 99%가 270 ms 이내에 완료
```

Average latency만 사용하는 경우 일부 느린 실행을 확인하기 어렵기 때문에 P95와 P99를 함께 기록했다.

### 13. 현재 결과의 한계


마찬가지로:

```text

```

도 모델 자체의 inference throughput이 아니라 현재 실행 구조 전체의 처리량이다.

## V0.2-B — Persistent Process Baseline Benchmark

### 1. 목표

V0.2-A에서는 OpenVINO Hello Classification C Sample을 수정하지 않고 프로그램 자체를 100회 반복 실행하여 process-per-image 구조의 baseline을 측정했다.

그러나 이 구조에서는 각 실행마다 다음 작업이 반복된다.

```text
Process Start
↓
OpenVINO Initialization
↓
Model Load / Compile
↓
Image / Tensor Preparation
↓
Inference
↓
Process Exit
```

따라서 V0.2-A의 실행시간에는 순수 inference뿐만 아니라 프로세스 생성, 모델 로딩 및 컴파일 등의 비용이 반복적으로 포함된다.

V0.2-B에서는 하나의 프로세스 안에서 모델과 input tensor를 한 번 준비한 뒤 동일한 input tensor에 대해 synchronous inference를 100회 반복하는 구조를 만든다.

목표는 다음 두 가지이다.

1. persistent process 구조의 전체 실행시간을 측정한다.
2. `ov_infer_request_infer()` 자체의 latency 분포를 측정한다.

이 단계 역시 최적화 단계가 아니다.

다음 기능은 추가하지 않는다.

```text
Thread          X
Async           X
Pipeline        X
Scheduler       X
Memory Pool     X
GPU Scheduling  X
```

따라서 V0.2-A와 달리 다음 작업은 매 inference마다 반복되지 않는다.

```text

```

### 4. Workload 정의

현재 V0.2-B workload는 서로 다른 이미지 100장을 처리하는 구조가 아니다.

`banana.bmp`를 한 번 읽고 input tensor를 한 번 생성한 뒤 동일한 tensor를 사용하여 inference를 100회 수행한다.

```text
banana.bmp
↓
Input Tensor 생성
↓
Inference #1
↓
Inference #2
↓
Inference #3
↓
...
↓
Inference #100
```

따라서 현재 workload는 다음과 같이 정의한다.

```text
1 Process
1 Model Load
1 Model Compile
1 Input Tensor
100 Synchronous Inference Calls
```

이 조건은 이후 benchmark 결과를 해석할 때 중요한 제한사항이다.

### 12. Inference Latency 측정 방법

전체 프로세스 실행시간과 별도로 `ov_infer_request_infer()` 자체의 latency를 측정하기 위해 프로그램 내부에 timing instrumentation을 추가했다.

시간 측정에는 다음 API를 사용했다.

```c
clock_gettime(CLOCK_MONOTONIC, ...)
```

각 inference는 다음 범위에서 측정된다.

```text
clock_gettime(start)
↓
ov_infer_request_infer()
↓
clock_gettime(end)
```

latency는 다음과 같이 millisecond 단위로 변환한다.

```c
double latency_ms =
    (end.tv_sec - start.tv_sec) * 1000.0
    + (end.tv_nsec - start.tv_nsec) / 1000000.0;
```

100개의 latency sample을 배열에 저장한 뒤 평균값을 계산했다.

또한 latency 배열을 오름차순으로 정렬하고 100개 sample을 기준으로 다음 위치의 값을 사용했다.

```text
P95 → sorted index 94
P99 → sorted index 98
```

즉 현재 구현에서는 100개 sample에 대해 단순 nearest-rank 방식으로 percentile을 계산한다.

### 17. 현재 결과의 한계

현재 V0.2-B benchmark에는 몇 가지 중요한 제한사항이 있다.

첫째, 실제 서로 다른 이미지 100장을 처리한 것이 아니다.

```text
Same Input Tensor
× 100 Inference Calls
```

구조이므로 실제 image-serving workload와 동일하다고 볼 수 없다.

둘째, 현재 inference latency는 synchronous inference의 API 호출 구간만 측정한다.

따라서 다음 비용은 inference latency에 포함되지 않는다.

```text
Image I/O
Image decoding
Tensor creation
Model loading
Model compilation
Application-level result processing
```

셋째, 100회의 inference sample만을 사용하고 있으므로 tail latency를 정밀하게 분석하기에는 sample 수가 제한적이다.

특히 P99는 100개의 sample에서 극단부에 위치하기 때문에 이후 더 큰 workload를 사용할 경우 다시 측정할 필요가 있다.

넷째, 현재 단계에서는 warm-up inference를 별도로 제거하지 않았다.

따라서 초기 inference가 이후 inference와 다른 특성을 보이는지 여부는 아직 분석하지 않았다.

이러한 항목들은 현재 결과가 잘못되었다는 의미가 아니라 V0.2-B baseline의 측정 범위를 정의하는 조건이다.
