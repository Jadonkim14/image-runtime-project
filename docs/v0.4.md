# V0.4 — Profiling and CPU Thread Scaling

## 1. 목표

V0.3에서는 이미지 분류 프로그램의 실행 단계를 나누고 각 단계의 시간을 측정했다.

V0.4의 목표는 단순한 stage-level timing을 넘어 Linux profiling 도구를 사용하여 CPU가 실제로 어디에서 시간을 사용하는지 확인하는 것이다.

주요 질문은 다음과 같다.

- CPU time은 어디에서 소비되는가?
- OpenVINO inference 내부에서는 어떤 실행 경로가 사용되는가?
- 동기식 inference는 하나의 CPU만 사용하는가?
- CPU thread 수를 변경하면 latency와 throughput은 어떻게 변하는가?
- thread 수 증가에 따라 성능이 계속 선형적으로 증가하는가?

## 3. Profiling Workload

기존 V0.3 프로그램에는 model loading, image loading, preprocessing, model compilation, inference 등이 모두 포함되어 있다.

전체 프로세스를 그대로 profiling하면 one-time initialization 비용과 반복 inference 비용이 섞이게 된다.

따라서 V0.4에서는 inference 실행 경로를 더 명확하게 관찰하기 위해 profiling 전용 workload를 구성했다.

```c
#define INFERENCE_COUNT 10000

for (int i = 0; i < INFERENCE_COUNT; i++) {
    CHECK_STATUS(ov_infer_request_infer(infer_request));
}
```

동일한 input tensor를 사용하여 synchronous inference를 10,000회 반복했다.

이 workload의 목적은 실제 production workload를 재현하는 것이 아니라 inference가 CPU profile에서 충분한 비중을 차지하도록 만드는 것이다.

따라서 이후 결과는 다음과 같이 해석한다.

> inference-dominant synthetic workload

실제 multi-image serving throughput으로 해석하지 않는다.

## 4. `perf stat`

먼저 Linux `perf stat`을 사용하여 전체 프로세스의 hardware/software performance counter를 확인했다.

```bash
perf stat -- ./benchmark/v0.2-b/build/hello_classification_c \
    models/squeezenet1.1-7.onnx \
    data/images/banana.bmp \
    CPU
```

초기 측정에서 대표적으로 다음과 같은 결과를 얻었다.

```text
task-clock:     1265.78 ms
CPUs utilized: approximately 4.0
page-faults:    9682
branches:       219105649
branch-misses:  2965395
cpu-cycles:     3305500924
instructions:   3917947823
IPC:            approximately 1.2
elapsed:        0.287 s
```

여기서 중요한 관찰은:

```text
task-clock / elapsed time ≈ 4
```

라는 점이다.

즉 application에서는 한 번에 하나의 synchronous inference request를 실행하고 있지만, 내부적으로 CPU 하나만 사용하고 있는 것은 아니었다.

이 결과를 통해 다음을 구분할 수 있었다.

```text
Synchronous API
≠
Single-thread execution
```

OpenVINO CPU Runtime 내부에서는 여러 CPU execution resource가 사용되고 있었다.

## 5. `perf record` / `perf report`

다음으로 sampling profiler를 사용했다.

```bash
perf record -g -- ./benchmark/v0.4-inference-profile/build/hello_classification_c \
    models/squeezenet1.1-7.onnx \
    data/images/banana.bmp \
    CPU
```

결과는 다음 명령으로 확인했다.

```bash
perf report
```

profile에서는 다음 실행 경로들이 반복적으로 관찰되었다.

```text
libtbb
OpenVINO Intel CPU Plugin
OpenVINO internal execution path
JIT generated regions
```

`libtbb` 관련 주소가 높은 비중으로 나타났으며 call graph에서도 TBB와 OpenVINO CPU Plugin 실행 경로가 확인되었다.

이는 OpenVINO CPU inference 내부에서 병렬 runtime이 사용되고 있다는 관찰과 일치했다.

하지만 이 단계에서 다음과 같이 결론 내리지는 않았다.

```text
"TBB가 병목이다."
```

높은 CPU 비중을 차지한다는 사실만으로 해당 라이브러리가 병목이라는 의미는 아니기 때문이다.

## 6. Symbol Resolution 한계

`perf report`에서 일부 TBB 함수는 함수 이름 대신 address 형태로 표시되었다.

관련 shared library를 확인했다.

```bash
ldd ./benchmark/v0.4-inference-profile/build/hello_classification_c
```

TBB library도 확인했다.

```bash
file <libtbb.so path>
```

결과:

```text
ELF 64-bit
dynamically linked
stripped
```

즉 일부 symbol/debug information이 제거되어 있었고, OpenVINO 내부에는 JIT-generated code도 존재했다.

이 때문에 현재 환경에서는 모든 hot path를 세부 함수 또는 operator 수준까지 해석하는 데 한계가 있었다.

따라서 symbol resolution 자체를 계속 추적하기보다는 현재까지 확보한 evidence를 바탕으로 다음 실험으로 진행했다.

## 7. Inference-Dominant Profiling

초기 profile에는 다음과 같은 one-time 작업도 포함되어 있었다.

```text
Model Load
Model Compile
Image Load
Tensor Preparation
```

따라서 inference의 비중을 높이기 위해 synchronous inference를 10,000회 반복하는 workload를 사용하여 다시 profiling했다.

`perf record -g` 실행 결과 약:

```text
31.2 MB perf.data
422,014 samples
```

가 수집되었다.

이 profile에서도 TBB 및 OpenVINO CPU Plugin 관련 실행 경로가 높은 비중으로 관찰되었다.

따라서 초기 profile에서 보인 병렬 runtime 실행 경로가 단순히 model compilation과 같은 startup 단계 때문에 나타난 현상일 가능성은 낮아졌다.

하지만 stripped symbols와 JIT 영역 때문에 세부 operator-level bottleneck까지 특정하지는 못했다.

## 8. OpenVINO CPU Thread Configuration

profiling 결과를 바탕으로 OpenVINO CPU Runtime이 실제로 몇 개의 inference thread를 사용하는지 확인했다.

OpenVINO의 다음 property를 조회했다.

```text
INFERENCE_NUM_THREADS
```

C API에서는 다음과 같이 확인했다.

```c
char* inference_threads = NULL;

CHECK_STATUS(
    ov_compiled_model_get_property(
        compiled_model,
        "INFERENCE_NUM_THREADS",
        &inference_threads
    )
);

printf("INFERENCE_NUM_THREADS: %s\n", inference_threads);

ov_free(inference_threads);
```

기본 설정에서 실제 출력은:

```text
INFERENCE_NUM_THREADS: 8
```

이었다.

즉 현재 환경에서 OpenVINO CPU Plugin이 선택한 inference thread 수는 8이었다.

---

## 9. Thread Count 제어

thread scaling을 직접 실험하기 위해 model compile 전에 property를 설정했다.

```c
CHECK_STATUS(
    ov_core_set_property(
        core,
        device_name,
        "INFERENCE_NUM_THREADS",
        argv[4]
    )
);
```

프로그램 실행 시 thread 수를 argument로 전달하도록 변경했다.

예:

```bash
./benchmark/v0.4-inference-profile/build/hello_classification_c \
    models/squeezenet1.1-7.onnx \
    data/images/banana.bmp \
    CPU \
    4
```

property readback을 통해 실제 설정값도 확인했다.

```text
INFERENCE_NUM_THREADS: 4
```

이제 동일한 binary와 workload에서 inference thread 수만 변경할 수 있게 되었다.

## 10. Inference Timing 방법

10,000개의 inference 각각에 timer를 삽입하면 측정 자체의 overhead가 반복적으로 발생한다.

따라서 V0.4 scaling 실험에서는 전체 inference loop의 시작과 끝만 측정했다.

```c
clock_gettime(CLOCK_MONOTONIC, &start);

for (int i = 0; i < INFERENCE_COUNT; i++) {
    CHECK_STATUS(ov_infer_request_infer(infer_request));
}

clock_gettime(CLOCK_MONOTONIC, &end);
```

그 후 다음 값을 계산했다.

```text
Total Inference Time

Average Inference Time
= Total Inference Time / 10000

Inference Throughput
= 10000 / Total Inference Time
```

여기서 throughput은 하나의 synchronous request를 순차적으로 반복한 처리율이다.

따라서 concurrent server throughput을 의미하지 않는다.

## 11. Thread Scaling Experiment

다음 thread 수를 비교했다.

```text
1
2
4
8
```

각 설정을 3회 반복했다.

### 평균 결과

| Threads | Avg Inference Time | Throughput | task-clock | CPUs Utilized |
|---:|---:|---:|---:|---:|
| 1 | 3.460 ms | 289.00 infer/s | 34.765 s | 1.0 |
| 2 | 1.996 ms | 501.04 infer/s | 40.045 s | 2.0 |
| 4 | 1.386 ms | 721.88 infer/s | 55.588 s | 4.0 |
| 8 | 1.346 ms | 743.22 infer/s | 107.905 s | 7.9 |

---

## 12. Scaling 분석

throughput 증가율은 다음과 같았다.

```text
1 → 2 threads
+73.4%

2 → 4 threads
+44.1%

4 → 8 threads
+3.0%
```

thread를 증가시키면 처음에는 큰 성능 향상이 발생했다.

하지만:

```text
4 → 8
```

구간에서는 추가 성능 향상이 크게 감소했다.

동시에 `perf stat`의 CPU resource 사용량은:

```text
4 threads
task-clock ≈ 55.6 s
CPUs utilized ≈ 4.0

8 threads
task-clock ≈ 107.9 s
CPUs utilized ≈ 7.9
```

로 증가했다.

즉 4 → 8 threads에서 CPU execution resource는 크게 증가했지만 synchronous inference throughput 향상은 약 3%에 그쳤다.

이를 통해 현재 workload에서 thread scaling에 **diminishing returns**가 존재한다는 것을 확인했다.

---

## 13. CPU Cost per Inference

전체 process의 `task-clock`을 10,000회 inference 수로 나누어 CPU resource cost를 비교했다.

대략적인 값은 다음과 같다.

```text
1 thread : 3.48 ms CPU time / inference
2 threads: 4.00 ms CPU time / inference
4 threads: 5.56 ms CPU time / inference
8 threads: 10.79 ms CPU time / inference
```

주의할 점은 `perf stat`의 task-clock이 전체 process를 측정하므로 이 값은 순수한 inference CPU time은 아니다.

하지만 10,000회 inference가 실행되는 inference-dominant workload이므로 thread 설정 간 CPU resource cost를 비교하는 지표로 사용했다.

---

## 14. 해석

V0.4에서 확인한 핵심 결과는 다음과 같다.

1. synchronous inference API를 사용한다고 해서 내부 실행이 single-threaded인 것은 아니다.

2. OpenVINO CPU Plugin은 현재 환경에서 기본적으로 `INFERENCE_NUM_THREADS=8`을 사용했다.

3. thread 수를 1 → 2 → 4로 증가시키면 큰 throughput 향상이 나타났다.

4. 4 → 8에서는 throughput 증가가 약 3%로 크게 감소했다.

5. 반면 8 threads에서는 약 7.9 CPUs가 사용되었으며 task-clock도 크게 증가했다.

따라서 현재 workload에서는:

```text
more threads
≠
proportional performance improvement
```

라는 것을 확인했다.

## 15. 이 단계에서 결론 내릴 수 없는 것

현재 결과만으로 다음과 같은 주장은 할 수 없다.

```text
"TBB가 병목이다."

"4 threads가 최적이다."

"OpenVINO의 기본 8-thread 설정이 비효율적이다."

"모든 OpenVINO workload에서 4 threads가 더 좋다."
```

이번 실험은:

```text
AMD Ryzen 7 PRO 7840U
WSL2
OpenVINO 2026.4.0
SqueezeNet 1.1
single synchronous infer request
same input tensor repeated 10,000 times
```

이라는 특정 환경에서 수행되었다.

또한 동일 tensor를 반복 사용했기 때문에 실제 여러 이미지가 들어오는 production workload와는 차이가 있다.

## 16. Benchmark Environment 관련 관찰

V0.4 이후 validation 과정에서 노트북의 전원 상태가 benchmark 결과에 큰 영향을 줄 수 있다는 사실도 발견했다.

Windows 설정은 다음과 같았다.

```text
AC connected:
Power mode = Balanced

Battery:
Power mode = Best power efficiency
```

동일한 8-thread workload를 사용한 A-B-A 실험에서는:

```text
AC connected
Throughput ≈ 781.59 infer/s
Avg latency ≈ 1.279 ms

Battery
Throughput ≈ 432.17 infer/s
Avg latency ≈ 2.314 ms

AC reconnected
Throughput ≈ 781.08 infer/s
Avg latency ≈ 1.280 ms
```

가 관찰되었다.

두 AC 측정값은 거의 동일하게 재현되었고 battery 상태에서는 큰 성능 감소가 발생했다.

모든 경우에서 약 7.9 CPUs가 사용되었으므로 단순히 실행 thread 수가 줄어든 현상으로 설명할 수는 없었다.

WSL2 환경에서는 표준 Linux `cpufreq` interface를 사용할 수 없었기 때문에 실제 CPU frequency/power limit의 변화를 직접 검증하지는 못했다.

따라서 다음과 같이만 결론 내린다.

> AC/Battery 상태 및 Windows power policy는 현재 benchmark 결과에 큰 영향을 주는 실험 변수였다.

구체적인 hardware power-limit mechanism까지 특정하지 않는다.

이후 benchmark에서는 다음 조건을 고정한다.

```text
AC: Connected
Windows plugged-in power mode: Balanced
```

## 17. V0.4에서 배운 것

V0.4에서는 단순히 `perf` 명령 사용법만 확인한 것이 아니다.

다음과 같은 성능 분석 과정을 경험했다.

```text
Stage Timing
↓
perf stat
↓
perf record / report
↓
Call Graph
↓
Symbol Resolution 한계 확인
↓
Inference-Dominant Workload 구성
↓
Runtime Configuration 발견
↓
Controlled Thread Scaling Experiment
↓
CPU Resource vs Performance 비교
```

특히 중요한 점은 profile에서 높은 비중을 차지하는 library를 발견했다고 바로 병목으로 판단하지 않았다는 것이다.

측정 결과를 기반으로 검증 가능한 runtime parameter를 찾고, 해당 parameter를 직접 통제하여 scaling experiment로 연결했다.

## 18. V0.4 결론

V0.4 profiling을 통해 OpenVINO CPU inference가 내부적으로 여러 CPU execution resource를 사용하고 있음을 확인했다.

`INFERENCE_NUM_THREADS`를 직접 제어하여 1, 2, 4, 8 threads를 비교한 결과, thread 증가에 따라 성능은 향상되었지만 scaling은 선형적이지 않았다.

특히:

```text
4 → 8 threads

CPU resource usage: 크게 증가
Throughput: 약 +3%
```

라는 diminishing returns가 관찰되었다.

하지만 이것만으로 4 threads가 더 좋은 설정이라고 결정할 수는 없다.

성능뿐 아니라 CPU resource consumption을 함께 고려한 명확한 최적화 목표와 검증 기준이 필요하다.

따라서 V0.5에서는 다음 가설을 검증한다.

> INFERENCE_NUM_THREADS를 8에서 4로 줄이면 CPU resource consumption을 크게 줄이면서 synchronous inference performance의 대부분을 유지할 수 있는가?

V0.5에서는 이 가설에 대해 사전에 성공 기준을 정의하고 별도의 validation experiment를 수행한다.
