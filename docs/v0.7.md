# V0.7 — Memory Allocation & Data Movement Analysis

## 1. 목표

V0.6에서는 Multi-Image Pipeline을 구축하고 OpenVINO Async Infer Request를 이용해 application-level concurrency를 증가시켰다.

Request concurrency를 `1 / 2 / 4 / 8`로 변경하여 측정한 결과, 현재 benchmark 조건에서는 **4-request Async configuration이 가장 높은 평균 throughput**을 기록하였다.

```text
Sequential     635.294 img/s
2 Requests     657.055 img/s
4 Requests     705.396 img/s
8 Requests     675.058 img/s
```

따라서 V0.7에서는 V0.6에서 확보한 **4-request Async Pipeline을 새로운 baseline**으로 사용한다.

V0.7의 목표는 새로운 최적화 기법을 바로 구현하는 것이 아니라, 현재 pipeline에서 발생하는 **memory allocation, deallocation 및 data movement 비용을 먼저 분석하는 것**이다.

현재 이미지 하나가 처리되는 과정에는 다음과 같은 메모리 관련 작업이 존재한다.

```text
Image Load
    ↓
Image Buffer
    ↓
Tensor Creation
    ↓
Input Tensor Set
    ↓
Inference
    ↓
Result Processing
    ↓
Tensor / Image Cleanup
```

Multi-Image workload에서는 이 과정이 이미지마다 반복되므로, buffer와 tensor의 반복적인 생성·해제 또는 불필요한 data copy가 존재한다면 전체 throughput에 영향을 줄 가능성이 있다.

그러나 V0.7 시작 시점에서는 **memory operation이 실제 성능 병목이라고 가정하지 않는다.**

먼저 다음 질문에 답하는 것을 목표로 한다.

> **현재 4-request Async Pipeline에서 반복적인 memory allocation/deallocation 또는 data movement가 전체 처리 성능에 의미 있는 비용을 발생시키는가?**

이를 확인하기 위해 현재 코드의 memory lifecycle을 추적하고, 이미지 한 장 및 전체 workload 처리 과정에서 어떤 메모리가 생성·재사용·해제되는지 분석한다.

필요한 경우 allocation 횟수, memory copy, memory usage 및 관련 실행 비용을 측정한다.

전체 진행 방식은 다음과 같다.

```text
V0.6 4-Request Async Baseline
            ↓
Memory Lifecycle Analysis
            ↓
Allocation / Free / Copy 측정
            ↓
Problem 존재 여부 판단
            ↓
        ┌───┴───┐
        │       │
      있음      미미함
        │       │
        ↓       ↓
Cause Analysis  결과 기록
        │       │
        ↓       └──→ 다음 단계
Optimization Hypothesis
        ↓
Buffer Reuse / Pre-allocation 등
        ↓
Implementation
        ↓
Re-measure
        ↓
Before / After 비교
```

따라서 V0.7의 핵심은 **Memory Pool이나 Buffer Reuse를 구현하는 것 자체가 아니라, 현재 pipeline의 memory behavior를 측정하고 실제 문제가 확인된 경우에만 최적화를 적용하는 것**이다.

V0.7에서도 이전 버전과 동일하게 다음 원칙을 유지한다.

```text
Measure
   ↓
Problem
   ↓
Cause
   ↓
Hypothesis
   ↓
Implementation
   ↓
Re-measure
```

## 2. Baseline 및 분석 대상

V0.7은 V0.6에서 가장 높은 평균 throughput을 기록한 **4-request Async configuration**을 baseline으로 사용하였다.

```text
4 Requests
Throughput: 705.396 img/s
```

분석 대상은 이미지 한 장이 처리되는 과정에서 반복적으로 발생하는 memory operation이다.

```text
Image Load
    ↓
Input Buffer
    ↓
Tensor
    ↓
Inference
    ↓
Output Tensor
    ↓
Result Buffer
    ↓
Cleanup
```

먼저 실제 코드의 memory lifecycle을 추적하여 allocation과 data copy가 발생하는 위치를 확인하였다.

---

## 3. Input Memory Lifecycle 분석

현재 benchmark에서는 OpenCV 경로가 아니라 OpenVINO sample의 BMP reader가 사용되고 있었다.

이미지 입력 과정은 다음과 같다.

```text
readBmpImage()
    ↓
malloc(image size)
    ↓
fread()
    ↓
image->data
    ↓
img->mat_data = bmp.data
    ↓
OpenVINO Tensor
```

`readBmpImage()`에서는 이미지마다 최종 pixel buffer를 `malloc()`으로 생성한다.

```c
image->data = malloc(size);
```

이후 BMP pixel data는 `fread()`를 통해 해당 buffer에 직접 저장된다.

따라서 별도의 full-image intermediate buffer를 생성한 뒤 다시 복사하는 과정은 확인되지 않았다.

또한 input tensor는 기존 image buffer를 이용하여 생성된다.

```c
ov_tensor_create_from_host_ptr(
    input_type,
    input_shapes[slot],
    images[slot].mat_data,
    &tensors[slot]
);
```

따라서 현재 input path에서는 image buffer와 별도로 동일한 pixel data를 저장하는 Tensor buffer를 생성하는 구조가 아니었다. OpenVINO의 host-memory Tensor 역시 기존 host memory를 감싸는 방식이며 내부 storage를 새로 할당하지 않는다.

---

## 4. Memory Deallocation Correctness 수정

Memory lifecycle을 분석하는 과정에서 allocation과 deallocation 방식이 일치하지 않는 부분을 발견하였다.

BMP reader에서는:

```c
image->data = malloc(size);
```

를 사용했지만 기존 non-OpenCV `image_free()`에서는:

```cpp
delete img->mat_data;
```

를 사용하고 있었다.

V0.7에서는 OpenVINO 설치 디렉터리의 원본 sample을 직접 수정하지 않고, `opencv_c_wrapper`를 프로젝트 내부로 복사하여 관리하도록 변경하였다.

이후 deallocation을 다음과 같이 수정하였다.

```cpp
std::free(img->mat_data);
img->mat_data = NULL;
```

이 변경은 성능 최적화가 아니라 **memory management correctness 수정**이다.

## 5. Input Allocation Cost 측정

반복적인 image buffer allocation이 실제 성능에 영향을 주는지 확인하기 위해 `malloc()` 호출 횟수와 실행시간을 직접 계측하였다.

2000 image workload 실행 결과:

```text
Malloc Count: 2001
Total Malloc Time: 0.283824 ms
Average Malloc Time: 0.000141841 ms/call
```

대표 이미지 로딩을 포함하여 총 2001회의 allocation이 발생하였다.

동일 실행의 전체 처리시간은:

```text
Total Processing Time: 2869.227 ms
```

였으며, 전체 실행시간에서 input `malloc()`이 차지한 비율은 약:

```text
0.01%
```

수준이었다.

따라서 반복적인 input buffer allocation은 존재하지만, 현재 workload에서는 의미 있는 성능 병목으로 판단하기 어려웠다.

## 6. Result Processing Memory 분석

다음으로 inference 결과 처리 과정의 memory behavior를 분석하였다.

`tensor_to_infer_result()`에서는 이미지마다 새로운 result buffer를 생성한다.

```c
struct infer_result* results =
    malloc(sizeof(struct infer_result) * result_size);
```

이후 output tensor의 값을 result buffer로 복사한다.

```c
for (i = 0; i < result_size; ++i) {
    results[i].class_id = i;
    results[i].probability = float_data[i];
}
```

마지막으로 전체 result를 정렬한다.

```c
qsort(
    results,
    result_size,
    sizeof(struct infer_result),
    compare
);
```

따라서 Result Processing을 다음 세 단계로 나누어 측정하였다.

```text
Result Buffer Allocation
        ↓
Tensor → Result Copy
        ↓
Result Sort
```

---

## 7. Result Processing 세부 측정

2000 image workload 기준 측정 결과:

```text
Result Malloc: 1.864975 ms total
Result Copy:   8.886836 ms total
Result Sort: 249.002331 ms total
```

Result Processing 내부 비중은 대략 다음과 같았다.

```text
Result Malloc       ~0.7%
Result Copy         ~3.4%
Result Sort        ~95.9%
```

즉 result buffer의 allocation과 data copy는 존재하지만, 실제 비용의 대부분은 memory operation이 아니라 `qsort()`에서 발생하였다.

---

## 8. V0.7 결론

V0.7에서는 memory allocation과 data movement가 현재 pipeline의 주요 병목인지 확인하였다.

분석 결과:

```text
Input Buffer
- 이미지마다 malloc 발생
- 별도 full-image copy 없음
- Tensor는 기존 host buffer 사용

Input malloc
- 2001 calls
- Total 0.284 ms
- 전체 처리시간의 약 0.01%

Result Buffer
- 이미지마다 malloc 발생
- Tensor → Result copy 발생

Result Processing
- Malloc: 1.865 ms
- Copy:   8.887 ms
- Sort: 249.002 ms
```

따라서 현재 workload에서는 **memory allocation 및 data copy 비용이 의미 있는 성능 병목이라는 근거를 확인하지 못했다.**

이 결과에 따라 V0.7에서는 다음 최적화를 적용하지 않았다.

```text
Buffer Pool
Buffer Reuse
Pre-allocation
```

측정 결과 성능 영향이 매우 작았기 때문에 이러한 구조를 추가하는 것은 현재 단계에서는 복잡도 증가에 비해 얻을 수 있는 효과가 제한적이라고 판단하였다.

---

## 9. 추가 관찰

Memory 분석 과정에서 Result Processing 비용의 대부분이 전체 결과에 대한 `qsort()`에서 발생한다는 점을 확인하였다.

```text
Memory Allocation / Copy
        ↓
작은 비중

Full Result Sort
        ↓
Result Processing의 대부분
```

이는 memory bottleneck은 아니지만 향후 별도의 optimization target이 될 수 있다.

예를 들어 실제 출력에 필요한 값이 Top-K뿐이라면 전체 result를 정렬하는 방식과 Top-K selection 방식의 비용을 비교할 수 있다.

다만 이는 V0.7의 Memory Allocation & Data Movement 범위를 벗어나므로 이번 버전에서는 추가 최적화를 진행하지 않았다.

---

## 10. V0.7 완료

V0.7에서 얻은 핵심 결론은 다음과 같다.

> **반복적인 memory allocation과 data movement는 실제 코드에 존재하지만, 현재 4-request Async workload에서 주요 성능 병목은 아니었다.**

따라서 측정 근거 없이 Buffer Pool이나 Pre-allocation을 추가하지 않고 현재 구조를 유지한다.

다음 버전에서는 이미지 처리 작업을 개별 **Job**으로 추상화하고 Queue와 Runtime이 작업을 관리할 수 있는 구조로 발전시킨다.

```text
V0.7
Memory Behavior Analysis
        ↓
No Significant Memory Bottleneck
        ↓
V0.8
Job / Queue / Runtime
```
