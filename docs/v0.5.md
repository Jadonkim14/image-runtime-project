# V0.5 — CPU Thread Configuration Optimization

## 1. 목표

V0.4에서는 Linux `perf`와 OpenVINO runtime property를 이용하여 CPU inference의 thread scaling을 분석했다.

V0.4의 1 / 2 / 4 / 8 thread 실험에서 다음과 같은 평균 throughput을 관찰했다.

```text
1 thread : 289.00 infer/s
2 threads: 501.04 infer/s
4 threads: 721.88 infer/s
8 threads: 743.22 infer/s
```

특히:

```text
4 → 8 threads
```

구간에서는 CPU execution resource가 크게 증가했지만 throughput 향상은 약 3%에 그쳤다.

따라서 V0.5에서는 단순히 최대 throughput을 얻는 것이 아니라:

> CPU resource consumption을 줄이면서 synchronous inference performance의 대부분을 유지할 수 있는가?

를 검증한다.

---

## 2. Optimization Target

V0.4에서 확인한 OpenVINO의 기본 설정은:

```text
INFERENCE_NUM_THREADS = 8
```

이었다.

V0.5에서는 이를:

```text
8 threads
↓
4 threads
```

로 변경하는 것을 optimization candidate로 선택했다.

변경 대상은 application의 algorithm이나 model이 아니라 OpenVINO CPU Runtime의 inference thread configuration이다.

---

## 3. 가설

V0.5의 가설은 다음과 같다.

> `INFERENCE_NUM_THREADS`를 8에서 4로 줄이면 CPU resource consumption을 크게 감소시키면서 synchronous inference performance의 대부분을 유지할 수 있다.

여기서 중요한 것은 단순히 CPU 사용량이 감소하는지만 확인하는 것이 아니다.

thread를 절반으로 줄이면 CPU 사용량이 감소하는 것은 예상할 수 있다.

따라서 다음 두 요소를 함께 평가한다.

```text
CPU Resource Cost
+
Inference Performance
```

---

## 4. 사전 성공 기준

결과를 본 뒤 성공 기준을 변경하지 않기 위해 validation 전에 기준을 먼저 정의했다.

| Metric | Success Criterion |
|---|---:|
| CPU usage reduction | ≥ 40% |
| Throughput decrease | ≤ 5% |
| Average latency increase | ≤ 5% |
| Classification result | Identical |

이 수치들은 일반적인 industry standard가 아니다.

현재 프로젝트에서 optimization hypothesis를 검증하기 위해 사전에 정의한 기준이다.

따라서 실험 후 결과가 기준을 조금 초과하더라도 기준 자체를 변경하지 않는다.

---

## 5. Validation Workload

V0.4와 동일한 inference-dominant workload를 사용했다.

```text
Model:
SqueezeNet 1.1

Input:
banana.bmp

Device:
CPU

Inference Count:
10,000

Execution:
Single synchronous inference request

Input Tensor:
Same tensor reused for all inference calls
```

비교 대상은:

```text
Baseline : 8 threads
Candidate: 4 threads
```

이다.

이 workload는 실제 multi-image production workload를 재현하기 위한 것이 아니다.

동일한 inference 작업을 충분히 반복하여 thread configuration에 따른 CPU resource consumption과 synchronous inference performance를 비교하기 위한 synthetic workload이다.

---

## 6. Interleaved Validation

시간 순서에 따른 system state 변화의 영향을 줄이기 위해 다음과 같이 실행 순서를 구성했다.

```text
8
4
8
4
8
4
```

즉:

```text
Run 1 → 8 threads
Run 2 → 4 threads
Run 3 → 8 threads
Run 4 → 4 threads
Run 5 → 8 threads
Run 6 → 4 threads
```

형태로 측정했다.

완전한 randomized experiment는 아니지만:

```text
8, 8, 8
→
4, 4, 4
```

처럼 한 설정을 모두 측정한 뒤 다른 설정을 측정하는 방식보다 시간 순서에 따른 영향을 줄이기 위한 구조이다.

---

## 7. 첫 번째 Validation에서 발생한 문제

초기 V0.5 validation에서 V0.4와 비교하여 전체 성능이 크게 감소했다.

대표적으로 8-thread 결과는 약:

```text
Average Inference Time ≈ 2.38 ms
Throughput ≈ 421 infer/s
```

수준이었다.

반면 V0.4에서는 8-thread workload가 약:

```text
Average Inference Time ≈ 1.35 ms
Throughput ≈ 743 infer/s
```

수준이었다.

동일한 binary와 workload를 사용했음에도 차이가 너무 컸기 때문에 이 결과를 바로 4-vs-8 optimization 결과로 사용하지 않았다.

먼저 benchmark environment를 조사했다.

---

## 8. Power State라는 Confounding Variable

실험 당시 Windows의 power configuration을 확인한 결과:

```text
AC connected:
Power mode = Balanced

Battery:
Power mode = Best power efficiency
```

로 설정되어 있었다.

즉 charger 연결 여부에 따라 Windows의 power policy 자체가 달라지는 환경이었다.

이 변수가 실제 benchmark 결과에 영향을 주는지 확인하기 위해 동일한 8-thread workload를 사용하여 A-B-A 실험을 수행했다.

```text
A1: AC connected
B : Battery
A2: AC reconnected
```

---


### B — Battery

```text

```

### A2 — AC Reconnected

```text

task-clock:             102694.62 ms

```

두 AC 결과는 거의 동일하게 재현되었다.

```text

```

반면 battery에서는:

```text

```

까지 성능이 감소했다.

따라서 charger/power state가 현재 benchmark 결과에 큰 영향을 주는 실험 변수라는 강한 evidence를 얻었다.

---

## 10. Power Experiment 해석의 한계

A-B-A 실험으로 다음은 확인할 수 있다.

```text
AC/Battery 상태 변화
↕
큰 benchmark performance 변화
```

하지만 이것만으로 구체적인 hardware mechanism까지 확인한 것은 아니다.

예를 들어:

```text
"CPU power limit이 정확히 얼마로 변경되었다."

"CPU clock이 정확히 특정 값으로 제한되었다."
```

와 같은 주장은 하지 않는다.

WSL2에서는 표준 Linux `cpufreq` interface를 사용할 수 없었기 때문에 CPU frequency/power policy를 Linux 측에서 직접 검증하는 데 한계가 있었다.

또한 `perf stat`의 `cpu-cycles` 옆에 표시되는 GHz 값을 Windows host CPU의 실제 clock frequency로 직접 해석하지 않는다.

따라서 현재 결과에서 확실하게 말할 수 있는 것은:

> AC/Battery 상태 및 이에 연결된 Windows power policy가 benchmark performance와 강하게 연관되어 있었으며, benchmark 환경에서 통제해야 할 변수였다.

라는 점이다.

```text

↓
```

```text

```


따라서 CPU resource consumption은 크게 감소했다.


```text

```

## 17. Hypothesis Result

V0.5에서 세운 가설은:

> `INFERENCE_NUM_THREADS`를 8에서 4로 줄이면 CPU resource consumption을 크게 감소시키면서 synchronous inference performance의 대부분을 사전에 정의한 범위 내에서 유지할 수 있다.

였다.

최종 결과:

```text
CPU resource reduction:
PASS

Throughput requirement:
FAIL

Latency requirement:
FAIL

Correctness:
PASS
```

따라서 사전에 정의한 성공 기준에 따르면:

> **V0.5 optimization hypothesis is rejected.**

결과를 확인한 후 5% 기준을 7% 또는 10%로 변경하여 성공으로 재분류하지 않는다.

---

## 18. 실패한 Optimization에서도 얻은 결과

가설은 성공 기준을 만족하지 못했지만 실험 자체가 의미 없는 것은 아니다.

8 → 4 threads 변경으로:

```text
CPU resource consumption
≈ 49% reduction

Throughput
≈ 6.7% decrease

Average latency
≈ 7.2% increase
```

가 관찰되었다.

즉 현재 workload에서는 CPU execution resource를 거의 절반 수준으로 줄였을 때 synchronous inference performance 감소는 약 7% 수준이었다.

이는 V0.4에서 관찰한:

```text
4 → 8 threads에서 diminishing returns 발생
```

이라는 결과와 일관된다.

하지만 이를 근거로:

```text
"4 threads가 최적이다."
```

라고 결론 내리지는 않는다.

어떤 설정이 적절한지는 시스템의 목표에 따라 달라질 수 있다.

예를 들어:

```text
Maximum single-request performance
```

를 우선한다면 8 threads가 유리할 수 있다.

반대로 CPU resource를 다른 작업과 공유해야 하는 환경에서는 4-thread configuration의 resource/performance trade-off가 의미를 가질 수 있다.

이번 V0.5에서는 특정 deployment policy를 결정하는 것이 아니라 이 trade-off를 측정하는 데 초점을 둔다.

## 20. 이번 단계에서 배운 점

V0.5에서 가장 중요한 부분은 단순히 thread 수를 8에서 4로 변경한 것이 아니다.

성능 실험에서는 다음 과정이 중요하다는 것을 확인했다.

```text
Measure
↓
Form Hypothesis
↓
Define Success Criteria
↓
Run Experiment
↓
Detect Unexpected Result
↓
Investigate Experimental Environment
↓
Identify Confounding Variable
↓
Control Environment
↓
Re-measure
↓
Accept or Reject Hypothesis
```

특히 첫 validation 결과가 예상과 크게 다르다고 해서 바로 optimization의 결과로 받아들이지 않았다.

전원 상태라는 외부 변수를 발견하고 별도의 A-B-A 실험으로 확인한 후 benchmark 환경을 고정하여 다시 측정했다.

또한 최종 결과가 사전 기준에 근접했더라도 기준을 변경하지 않고 가설을 기각했다.

## 21. 한계

현재 V0.5에는 다음과 같은 한계가 있다.

### 1. 동일 Tensor 반복

10,000회의 inference가 모두 동일한 input tensor를 사용한다.

따라서 실제 여러 이미지가 입력되는 workload와 다르다.

### 2. Single Synchronous Request

현재 프로그램은 하나의 inference request를 순차적으로 실행한다.

따라서 측정된 throughput은 concurrent request 처리 성능이 아니다.

### 3. Whole-Process `perf stat`

`task-clock`은 inference loop만이 아니라 process 전체를 측정한다.

다만 10,000회의 inference가 workload 대부분을 차지하기 때문에 thread configuration 간 CPU resource 비교 지표로 사용했다.

### 4. WSL2

실험은 native Linux가 아니라 WSL2에서 수행되었다.

따라서 host Windows의 power management와 virtualization 환경이 benchmark에 영향을 줄 수 있다.

### 5. Single Model / Hardware

현재 결과는:

```text
SqueezeNet 1.1
AMD Ryzen 7 PRO 7840U
OpenVINO 2026.4.0
```

환경에서 얻은 결과이다.

다른 model이나 hardware로 일반화하지 않는다.

## 22. V0.5 결론

V0.5에서는 V0.4 profiling에서 발견한 CPU thread scaling 특성을 바탕으로 `INFERENCE_NUM_THREADS=8`에서 `4`로 줄이는 optimization candidate를 검증했다.

최종적으로:

```text
CPU resource consumption:
approximately 49% reduction

Throughput:
approximately 6.7% decrease

Average latency:
approximately 7.2% increase

Classification result:
identical
```

이라는 결과를 얻었다.

CPU resource 절감에는 성공했지만 throughput과 latency가 사전에 정의한 5% performance threshold를 초과했다.

따라서:

> **V0.5 optimization hypothesis는 사전에 정의한 기준에 따라 기각한다.**

그러나 이번 실험을 통해 현재 synchronous inference workload에서 4-thread와 8-thread 사이에 명확한 CPU-resource/performance trade-off가 존재한다는 것을 확인했다.

또한 benchmark 과정에서 AC/Battery power state가 성능에 큰 영향을 미치는 환경 변수임을 발견하여 이후 실험에서는 다음 조건을 benchmark standard로 고정한다.

```text
AC connected
Windows plugged-in power mode: Balanced
```

V0.4와 V0.5를 통해 profiling에서 시작하여 runtime parameter를 발견하고, controlled experiment를 설계하고, confounding variable을 찾아 제거한 뒤 가설을 검증하는 전체 performance engineering cycle을 수행했다.

다음 단계에서는 단일 tensor 반복 workload를 넘어 실제 여러 image job을 처리할 수 있는 workload 구조를 먼저 구성한 뒤 concurrent pipeline과 worker scaling을 검토한다.
