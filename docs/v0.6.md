# V0.6 — Multi-Image Pipeline & Async Request Concurrency Optimization

## 1. 목표

기존 benchmark는 사실상 하나의 이미지에 대해 inference를 반복 실행하는 구조였다.

V0.6에서는 이를 실제 여러 이미지를 처리할 수 있는 **Multi-Image Pipeline**으로 확장하고, 이후 concurrency 최적화를 평가할 수 있는 Sequential Baseline을 구축하는 것을 첫 번째 목표로 설정하였다.

초기 구조는 다음과 같다.

```text
Directory
   ↓
Image 1 → Tensor → Inference → Result
   ↓
Image 2 → Tensor → Inference → Result
   ↓
Image 3 → ...
```

이후 Sequential Pipeline을 profiling하여 병목을 측정하고, 그 결과를 기반으로 OpenVINO asynchronous inference와 multiple Infer Request를 적용한다.

전체 V0.6의 진행 방식은 다음과 같다.

```text
Multi-Image Pipeline
        ↓
Sequential Baseline
        ↓
Stage Profiling
        ↓
Problem / Cause Analysis
        ↓
Concurrency Hypothesis
        ↓
Async Implementation
        ↓
Request Scaling: 2 / 4 / 8
        ↓
perf CPU Utilization
        ↓
Re-measure & Analysis
```

핵심 원칙은 다음과 같다.

```text
Measure
   ↓
Problem
   ↓
Cause
   ↓
Hypothesis
   ↓
Implementation
   ↓
Re-measure
```

# 4. Dynamic Input Shape 적용

서로 다른 크기의 이미지를 하나의 compiled model에서 처리하기 위해 preprocessing model의 input H/W를 dynamic으로 변경하였다.

```c
ov_dimension_t dynamic_dims[4] = {
    {1, 1},
    {-1, -1},
    {-1, -1},
    {3, 3}
};
```

각 dimension의 의미는:

```text
N = 1
H = dynamic
W = dynamic
C = 3
```

따라서 input shape은:

```text
{1, ?, ?, 3}
```

이 된다.

이후:

```c
ov_model_reshape_single_input(
    new_model,
    dynamic_input_shape
);
```

를 수행한 뒤 model을 compile하였다.

# 6. Double Free 문제 해결

두 이미지의 inference 자체는 성공했지만 프로그램 종료 과정에서:

```text
double free or corruption (!prev)
Aborted
```

가 발생하였다.

Per-image loop 내부에서:

```c
image_free(&img);
```

를 수행한 뒤 최종 `err:` cleanup에서도 같은 image가 다시 해제될 가능성이 있었다.

따라서 per-image cleanup 이후:

```c
image_free(&img);
img = (c_mat_t){0};
```

로 상태를 초기화하였다.

그 결과 multi-image inference 이후 정상 종료까지 성공하였다.

# 7. Sequential Multi-Image Pipeline 완성

이 시점의 pipeline은 다음과 같다.

```text
Model Load
    ↓
Preprocessing Configuration
    ↓
Dynamic Shape {1, ?, ?, 3}
    ↓
Model Compile
    ↓
Infer Request Creation
    ↓
Directory Scan
    ↓
Image Load
    ↓
Tensor Creation
    ↓
Set Input Tensor
    ↓
Synchronous Inference
    ↓
Result Processing
    ↓
Per-image Cleanup
    ↓
Next Image
```

여기서 중요한 점은 **Model Compile과 Infer Request 생성은 한 번만 수행하고, 하나의 실행 환경에서 여러 이미지를 연속 처리한다는 것**이다.

# 8. Benchmark 통계 추가

Sequential baseline을 정량화하기 위해 처리 이미지 수를 기록하였다.

```c
size_t total_images = 0;
```

전체 multi-image processing 구간을 측정하여 다음 값을 출력하도록 하였다.

```text
Total Images
Total Processing Time
Average Time per Image
Throughput
```

계산식은 다음과 같다.

```text
Average Time per Image
= Total Processing Time / Total Images
```

```text
Throughput
= Total Images / Total Processing Time(seconds)
```

초기 구현에서는 `Average Latency`라는 이름을 사용했지만, Async Pipeline으로 확장한 이후 의미를 명확하게 하기 위해 최종적으로 **Average Time per Image**로 변경하였다.

이는 concurrent pipeline에서 `Total Processing Time / Total Images`가 개별 request의 실제 latency와 동일하지 않기 때문이다.

# 15. 문제 정의

Sequential 구조에서는 하나의 request가 완료된 이후 다음 이미지의 inference를 시작한다.

```text
Request 1
start
  ↓
inference
  ↓
complete
  ↓
Request 2
start
  ↓
inference
  ↓
complete
```

Stage profiling 결과 inference가 전체 처리시간의 대부분을 차지하고 있었다.

따라서 다음 질문을 설정하였다.

> 하나의 Infer Request 완료를 기다린 뒤 다음 request를 시작하는 대신 여러 request를 in-flight 상태로 유지하면 전체 throughput을 높일 수 있는가?

---

# 16. Concurrency Hypothesis

OpenVINO의 asynchronous inference API를 이용하여 여러 Infer Request를 동시에 in-flight 상태로 유지하도록 변경한다.

가설:

> Multiple Infer Request 기반 asynchronous execution을 사용하면 runtime이 실행 가능한 inference 작업을 더 지속적으로 확보할 수 있으며, sequential execution보다 전체 image throughput을 향상시킬 가능성이 있다.

단, Async API를 사용하는 것 자체가 성능 향상을 보장한다고 가정하지 않았다.

따라서 request concurrency를 직접 변경하면서 측정한다.

```text
1 → 2 → 4 → 8 requests
```

# 17. Async Infer Request Pool 구현

여러 request를 관리할 수 있도록 request pool을 구성하였다.

```c
#define NUM_REQUESTS 8

ov_infer_request_t* infer_requests[NUM_REQUESTS] = {NULL};

ov_tensor_t* tensors[NUM_REQUESTS] = {NULL};
ov_shape_t input_shapes[NUM_REQUESTS] = {0};
c_mat_t images[NUM_REQUESTS] = {0};

int slot_busy[NUM_REQUESTS] = {0};

size_t submitted_images = 0;
```

Infer Request는 compiled model에서 미리 생성한다.

```c
for (int i = 0; i < NUM_REQUESTS; i++) {
    CHECK_STATUS(
        ov_compiled_model_create_infer_request(
            compiled_model,
            &infer_requests[i]
        )
    );
}
```

각 이미지가 사용할 slot은:

```c
int slot = submitted_images % NUM_REQUESTS;
```

로 선택한다.

`total_images`가 아니라 `submitted_images`를 사용하는 이유는 `total_images`는 완료된 이미지 수를 나타내기 때문이다.

---

# 18. Request Slot 재사용

선택된 slot이 아직 사용 중이라면 해당 request가 완료될 때까지 기다린다.

```text
Select Slot
    ↓
Busy?
 ┌──┴──┐
No    Yes
      ↓
     Wait
      ↓
 Result Processing
      ↓
 Resource Cleanup
      ↓
Submit New Request
```

새 inference는:

```c
ov_infer_request_start_async(...)
```

를 사용하여 제출한다.

성공적으로 제출된 뒤:

```c
slot_busy[slot] = 1;
submitted_images++;
```

로 상태를 변경한다.

---

# 19. Final Drain

모든 이미지를 제출했다고 해서 모든 inference가 완료된 것은 아니다.

따라서 directory processing이 끝난 뒤 남아 있는 busy request들을 모두 기다린다.

```c
for (int slot = 0; slot < NUM_REQUESTS; slot++) {

    if (!slot_busy[slot])
        continue;

    ov_infer_request_wait(...);

    // Result processing
    // Resource cleanup

    slot_busy[slot] = 0;
}
```

이를 통해 마지막으로 제출된 request들의 결과까지 처리한다.

# 20. Async Timing 측정 방식 수정

처음에는:

```c
ov_infer_request_start_async()
```

전후 시간을 `Inference Time`으로 측정하였다.

하지만 이 값은 실제 inference duration이 아니다.

`start_async()`는 inference 완료를 기다리지 않고 작업을 제출한 뒤 반환하기 때문이다.

따라서 해당 metric을:

```text
Async Submit
```

으로 변경하였다.

또한:

```c
ov_infer_request_wait()
```

구간을 별도로 측정하여:

```text
Wait
```

으로 기록하였다.

Async stage breakdown:

```text
Image Load
Tensor Preparation
Input Tensor Set
Async Submit
Wait
Result Processing
Other
```

여기서:

```text
Async Submit
= inference 작업 제출 overhead

Wait
= main thread가 request 완료를 기다리며 block된 시간
```

이다.

`Wait`은 inference 자체의 순수 실행시간과 동일하지 않다.

Async execution에서는 runtime 내부 inference와 main-thread 작업이 시간적으로 겹칠 수 있으므로 각 stage의 시간을 Sequential Pipeline처럼 단순한 시간 구성비로 해석하지 않는다.

따라서 Async 성능의 주요 지표는:

```text
Total Processing Time
Average Time per Image
Throughput
Throughput Variability
CPU Utilization
```

로 설정하였다.

# 28. Saturation 분석

전체 데이터를 함께 보면:

```text
Requests     Throughput       CPU Utilization

2            657.1 img/s      ≈ 7.5 CPUs
4            705.4 img/s      ≈ 8.05 CPUs
8            675.1 img/s      ≈ 7.96 CPUs
```

2 → 4 request에서는 throughput과 CPU utilization이 함께 증가하였다.

그러나 4 → 8에서는 CPU utilization이 더 이상 증가하지 않았으며 throughput도 감소하였다.

현재 측정 결과는 **4-request 부근에서 현재 workload와 thread configuration의 concurrency benefit이 포화되기 시작했을 가능성**과 일관된다.

8개의 in-flight request를 제공해도 CPU 실행 자원의 평균 활용이 더 증가하지 않았기 때문이다.

추가적인 request 관리 비용, runtime scheduling overhead, resource contention 또는 cache pressure 등이 8-request 성능 감소에 영향을 주었을 가능성이 있다.

그러나 현재 측정만으로 그중 특정 원인을 직접 증명할 수 없으므로 원인으로 확정하지 않는다.

# 29. Throughput 안정성

평균 throughput만으로 configuration을 평가하면 실행 간 변동성을 놓칠 수 있다.

따라서 Coefficient of Variation(CV)을 함께 사용하였다.

```text
CV = Standard Deviation / Mean × 100%
```

CV가 낮을수록 반복 실행 결과가 평균 주변에 상대적으로 더 밀집되어 있다는 의미이다.

결과:

```text
1 request     ≈ 4.8%
2 requests    ≈ 9.9%
4 requests    ≈ 3.9%
8 requests    ≈ 6.8%
```

4-request configuration은 테스트한 Async configuration 중:

```text
가장 높은 Mean Throughput
+
가장 낮은 Throughput CV
```

를 기록하였다.

따라서 현재 실험 범위에서는 높은 평균 성능뿐 아니라 상대적으로 안정적인 반복 측정 결과도 보였다.

# 32. V0.6에서 확인한 것

V0.6의 핵심은 단순히 OpenVINO의 Async API를 적용한 것이 아니다.

실제 진행 과정은 다음과 같다.

```text
Single-image 구조
        ↓
Multi-image pipeline 구현
        ↓
Dynamic input shape 문제 발견
        ↓
Dynamic H/W 지원
        ↓
Memory cleanup 문제 해결
        ↓
Sequential benchmark 구축
        ↓
Console I/O benchmark distortion 발견
        ↓
Benchmark 환경 통제
        ↓
Stage profiling
        ↓
Inference bottleneck 확인
        ↓
Concurrency hypothesis 설정
        ↓
Async request pool 구현
        ↓
2 / 4 / 8 request scaling
        ↓
perf CPU utilization 측정
        ↓
Concurrency saturation 분석
```

이를 통해 다음 사실을 확인하였다.

### 1. Benchmark 환경 통제가 중요하다

Console logging과 power state만으로도 측정 결과가 크게 달라졌다.

따라서 optimization 전후 비교보다 먼저 benchmark 환경을 통제해야 한다.

### 2. 측정 없이 concurrency를 추가하면 안 된다

Sequential stage profiling에서 inference가 전체 처리시간의 약 82.7%를 차지한다는 것을 확인한 뒤 Async concurrency를 적용하였다.

즉 구현보다 먼저 병목을 측정하였다.

### 3. Async 자체가 성능 향상을 보장하지 않는다

2-request에서는 평균 throughput이 증가했지만 CV가 약 9.9%로 높았다.

따라서 Async API 사용 여부만으로 성능 개선을 판단할 수 없다.

### 4. Concurrency가 많을수록 항상 빠른 것은 아니다

Request 수를:

```text
1 → 2 → 4
```

로 증가시킬 때 throughput이 증가했지만:

```text
4 → 8
```

에서는 오히려 감소하였다.

### 5. CPU utilization과 throughput을 함께 봐야 한다

4-request에서는 약 8.05 CPUs를 사용하면서 가장 높은 평균 throughput을 기록하였다.

8-request에서는 약 7.96 CPUs로 CPU utilization이 더 증가하지 않았으며 throughput도 감소하였다.

따라서 단순 request 개수보다 실제 execution resource utilization을 함께 측정하는 것이 중요하다.

# 33. 결론

V0.6에서는 기존 single-image 중심 benchmark를 **dynamic-shape Multi-Image Pipeline**으로 확장하고, 반복 가능한 Sequential Baseline을 구축하였다.

이후 stage profiling을 통해 inference가 전체 processing time의 약 82.7%를 차지하는 주요 optimization target임을 확인하였다.

이를 기반으로 multiple Infer Request를 사용하는 asynchronous execution을 구현하고 request concurrency를:

```text
1 / 2 / 4 / 8
```

로 변경하면서 성능을 측정하였다.

그 결과 테스트한 configuration 중 4-request Async에서:

```text
705.396 images/sec
```

의 가장 높은 평균 throughput을 기록하였으며, Sequential Baseline:

```text
635.294 images/sec
```

대비 약:

```text
+11.0%
```

의 향상을 측정하였다.

하지만 request를 8개로 증가시키자 평균 throughput은:

```text
675.058 images/sec
```

로 감소하였다.

`perf stat` 측정에서도 4-request와 8-request가 각각 약:

```text
4 requests → 8.05 CPUs
8 requests → 7.96 CPUs
```

를 사용하여 추가 request가 평균 CPU utilization 증가로 이어지지 않았다.

따라서 현재 benchmark 조건에서는 request concurrency 증가에 따른 성능 향상이 일정 지점 이후 포화되며, **더 높은 application-level concurrency가 항상 더 높은 throughput을 의미하지 않는다는 것을 측정을 통해 확인하였다.**

V0.6의 최종 결과는 단순한 Async API 적용이 아니라:

> **Sequential baseline을 구축하고 실제 병목을 profiling한 뒤, concurrency를 단계적으로 증가시키면서 throughput, variability, CPU utilization을 함께 측정하여 현재 workload의 request concurrency scaling 특성과 saturation 구간을 분석한 것**

으로 정리할 수 있다.
